Foundations · 1 of 3

Modularity — the big idea

Everything in this prelab flows from one principle: break a complex task into the smallest possible specialized units, then wire them together.

Why one big agent breaks down

A single agent handling a large task has four compounding problems. Each one gets worse as the task grows.

Context overload

Every step adds tokens. Long tasks push earlier context out of the window — the agent "forgets" what it decided three steps ago.

No specialization

A prompt that does ten things is worse at each one than a prompt written just for that thing. Generalist prompts average down.

Hard to debug

When the output is wrong, which step failed? A monolithic agent gives you no answer. Modular agents give you a traceable step.

No parallelism

Independent subtasks run sequentially. You pay the latency of every step even when several could run at the same time.

The modularity solution

Decompose the task into the smallest possible specialized units — each with one job, one context, one output contract. Then wire them together using the four techniques you'll learn in this prelab.

TechniqueWhat it doesMain benefit
DelegationSpawn subagents from a skill's instructionsIsolated context per subtask
LoopingIterate until quality threshold is metSelf-correcting output
Det. scriptsReplace LLM calls with deterministic codeAccuracy + lower latency
ChainingSkills call other skills at the endComposable pipelines
The latency tradeoff Modularity has a cost: more agents means more round-trips. A sequential chain of five subagents takes five times the latency of one agent. Design for parallelism where you can, and only split what genuinely benefits from isolation.

Subagents in depth

A subagent is an agent running in its own isolated context. It knows nothing about what came before — only what it was given in this call.

What makes a subagent different

Isolated context

Each subagent gets a fresh context window. No bleed from earlier steps — and no risk of earlier errors compounding.

Skill-loaded

A subagent can have its own skill loaded — a focused set of instructions written specifically for its one job.

Spawned by instructions

The parent skill's instructions tell the orchestrator to spawn a subagent and what to pass it. This is what we're building in this prelab.

How spawning works

When a skill's instructions say "spawn a subagent for X," the orchestrator creates a new isolated agent call, passes it a specific input, and waits for the structured result. The parent then uses that result to continue.

What goes in a subagent skill

A subagent's skill is written the same way as any skill — but with much tighter constraints, since it has a very narrow job and the parent needs to parse its output reliably.

---
name: finding-hotels
description: >
  Finds hotel options for a given city and date range. Use when
  a trip-planning orchestrator needs accommodation options.
---

## Instructions

You receive a city name and travel dates. Return exactly 3 hotel options.

Output format — always use exactly this structure:
**Option 1:** [Name] — [price/night] — [one sentence on why it fits]
**Option 2:** [Name] — [price/night] — [one sentence on why it fits]
**Option 3:** [Name] — [price/night] — [one sentence on why it fits]

Do not add commentary, preambles, or caveats. Three options only.
Design rule: one job, one output contract A subagent should do exactly one thing and return a predictable, parseable result. If the parent skill can't reliably extract the subagent's output and pass it to the next step, the whole pipeline breaks.

Workflow patterns

Five patterns cover the vast majority of multi-agent systems. You'll use several of them together in the activities. Click each to expand.

A→C

Sequential

Steps run in order — output of each feeds the next

▼

Each subagent runs one after another. Simple, predictable, easy to debug. Use when each step genuinely depends on the previous result.

Watch out for: One failed step blocks everything downstream. Handle errors at each step.

//

Parallel

Independent subagents run at the same time, results merged

▼

Fan out to multiple subagents simultaneously when their inputs don't depend on each other. Merge results when all complete. Saves significant latency.

Watch out for: The slowest subagent determines total latency. Set timeouts and handle partial failures.

↺

Verification loop

Agent checks its own output, retries if it fails

▼

The agent generates output, runs a check (either itself or a subagent), and if it fails, retries with the feedback. Stops when it passes or hits a max retry limit.

Always cap retries. Define a max (e.g. 3) and a fallback for when it never passes.

if

Routing

A classifier decides which specialist to send work to

▼

A router reads the input and sends it to the right specialist agent. Use when different inputs need fundamentally different handling — different tools, different expertise, different output formats.

Watch out for: The router's accuracy is critical — a misclassification sends work to the wrong agent entirely. Test the router separately before relying on it in a pipeline.

E→O

Evaluator–optimizer

Evaluator subagent judges output, main agent improves it

▼

A specialization of the verification loop: the checker is a dedicated evaluator subagent with its own rubric, rather than the main agent checking its own work. Separation of concerns produces better feedback.

1
Main agent generates output.
2
Evaluator subagent scores it against a rubric — pass/fail + specific improvement notes.
3
Main agent re-generates using the evaluator's feedback. Loop until pass or max retries.

Why a separate evaluator? The main agent is bad at critiquing its own output — it rationalizes rather than identifies flaws. A separate agent with a different prompt is more objective.

Patterns combine Real systems mix these. A trip planner might use parallel (flights, hotels, itinerary at once) inside an orchestrator-worker structure, with a verification loop on the itinerary subagent. You pick per step, not per system.

Design Patterns · 1 of 4

Delegation & subagents

How to write a skill that spawns subagents — what goes in the instructions, how to pass inputs, and how to collect results.

Writing the orchestrator skill

The parent skill's instructions do three things: describe the overall goal, specify what to delegate and to which subagent, and define how to assemble the final answer from their results.

---
name: planning-trip
description: >
  Plans a complete trip with flights, hotels, and a daily itinerary.
  Use when a user provides a destination, travel dates, and budget.
---

## Instructions

You are a trip planning coordinator. Given a destination, dates, and budget:

1. Spawn the finding-flights subagent with: destination, dates, budget.
2. Spawn the finding-hotels subagent with: destination, dates, budget.
3. Spawn the building-itinerary subagent with: destination, dates.
4. Assemble all three outputs into a single trip plan using this format:

## ✈ Flights
[flights subagent output]

## 🏨 Hotels
[hotels subagent output]

## 📅 Itinerary
[itinerary subagent output]

Run steps 1–3 in parallel when possible to reduce total time.

Each subagent gets one job

Notice that each subagent skill is narrow — it receives a structured input and returns a structured output. The orchestrator never asks a subagent to "plan the whole trip" — it only asks it to handle one well-defined piece.

finding-flights

Input: destination, dates, budget.
Output: 3 flight options with price and airline.

finding-hotels

Input: destination, dates, budget.
Output: 3 hotel options with price and rating.

building-itinerary

Input: destination, dates.
Output: day-by-day activity plan.

The context isolation rule Subagents have no memory of each other and no access to the parent's context. If the finding-hotels subagent needs to know the budget, the orchestrator must pass it explicitly in the call — it cannot "just know."

How many subagents is too many?

Each subagent adds latency (if sequential) or complexity (if parallel). A good rule: split when the subtask genuinely needs different expertise, different tools, or needs to run in isolation. Don't split just for the sake of it.

Design Patterns · 2 of 4

Loop patterns

Loops are how agents improve their own output. The key design decisions are: what triggers a retry, who does the checking, and when do you stop?

Three types of loops

Fixed

Run N times

Repeat a fixed number of times, keep the best result. No evaluator needed. Use for diversity, not quality.

Conditional

Run until rule met

Stop when a deterministic condition passes — word count, format check, schema validation. Exit is objective.

Evaluator

Run until quality passes

A judge (the agent itself or a subagent) scores the output. Exit depends on a quality judgment, not a rule.

Verification loop — in a skill

Adding a verification loop to a skill means instructing the agent to check its own output before finalizing it. The check can be a rule ("is this under 100 words?") or a judgment ("does this cover all the points the user asked for?").

## Instructions

1. Generate a day-by-day itinerary for the destination and dates.
2. Check your itinerary against these criteria:
   - Every day has at least 2 activities
   - No day has more than 4 activities (realistic pacing)
   - Each activity has an estimated duration
3. If any criterion fails, revise the itinerary and check again.
4. Repeat until all criteria pass, or until you have tried 3 times.
5. Output your best attempt even if it doesn't fully pass at 3 tries.
Self-checking vs. subagent checking A self-check (the same agent verifies its own work) is simpler but less reliable — the agent rationalizes its mistakes. A subagent evaluator with a separate prompt is more objective. Use self-checks for mechanical criteria (word counts, field presence); use subagent evaluators for quality judgments.

Design Patterns · 3 of 4

Deterministic scripts

Not everything should be left to the LLM. If there is exactly one correct answer, write a script — it's faster, cheaper, and always right.

What makes something deterministic?

A task is deterministic if: given the same input, you always get the same output, and a human could write a unit test for it. Anything else involves judgment and belongs in the LLM.

Leave to the LLM
  • Classifying, summarizing, deciding
  • Writing or rewriting content
  • Judging quality or tone
  • Reasoning about nuance or context
Write a script for
  • Counting words, characters, items
  • Validating format (email, date, JSON)
  • Math calculations
  • API calls, database queries
  • Sorting, filtering, transforming data

Why it matters

Accuracy

An LLM might miscount, round, or hallucinate a value. A script is always exact.

Latency

A Python function runs in milliseconds. An LLM call takes seconds and adds tokens.

Debuggability

A failing script throws an error. A failing LLM call gives you a plausible-sounding wrong answer.

How to reference a script in a skill

You don't paste script code into the skill. You give the path and specify exactly which function to call and what it returns.

## Instructions

To count the number of words in a text:
Run: python scripts/count_words.py "[text]"
Returns: an integer (the word count).

Use this count before deciding whether the summary needs trimming.
Do NOT estimate or count manually — always use the script.
The golden rule If you would write a unit test for it, write a script. If you can't write a unit test for it, use the LLM.

Chaining skills

Skills can call other skills at the end of their procedure — making each skill a specialized step in a larger pipeline.

Skills calling skills

When a skill finishes its job, it can hand off to the next skill rather than returning to the user. This keeps each skill narrow and composable — the chain handles the full workflow.

planning-trip
orchestrates
calls
finding-flights
returns options
chains to
verifying-budget
checks cost
chains to
formatting-output
presents result

How to chain in a skill

At the end of a skill's instructions, specify which skill to call next and what to pass it.

## Instructions

# (finding-flights skill)
1. Search for available flights matching the provided criteria.
2. Return the top 3 options with price, airline, and duration.
3. When complete, pass your results to the
   verifying-budget skill along with the user's original budget.
   Format: "Flight options: [results]. User budget: [budget]"

Chaining vs. orchestrating

ChainingOrchestrating
Who controls flow?Each skill passes to the nextCentral orchestrator decides
Best forLinear pipelines, each step specialisedComplex branching, parallel steps
Error handlingEach skill handles its ownOrchestrator catches and reroutes
The main idea — modularity Whether you delegate, loop, script, or chain: the goal is the same. Each unit does one thing well, can be tested independently, and can be swapped out without touching anything else. This is what makes agent systems maintainable at scale.
