Prompt Engineering · 1 of 3

Zero-shot vs few-shot prompting

Before building agent skills, you need to write good prompts. This section covers the two most fundamental prompting strategies.

What is prompt engineering?

Prompt engineering is the process of designing and revising prompts to guide AI models toward more useful outputs. A better prompt does not guarantee a better answer, but it gives the model clearer information about the task, context, audience, format, and constraints.

The two baseline strategies

Zero-shot prompting

Give the AI a task with no examples. The model relies entirely on its training to figure out the expected format and style. Fast to write, but output shape can vary.

"Summarize this article in three bullet points."

Few-shot prompting

Give the AI a handful of input→output examples before your real task. The model learns the expected format and style from the examples, producing more consistent output.

"Here are two example summaries: [A], [B]. Now summarize this article the same way."

When to use which

SituationUse
Output format is flexible or the task is simpleZero-shot
Output needs a specific structure the model might not guessFew-shot
Your output format isn't landing right after zero-shotFew-shot
You want fast iteration and format isn't criticalZero-shot
The rule of thumb Start zero-shot. If the output format or tone isn't what you want, add 1–2 concrete examples showing exactly what you're looking for. Don't add examples just to add them — a bad example misleads the model more than no example at all.

Iterative prompt building

You rarely write the perfect prompt on the first try. The technique is to start minimal and add one element at a time, testing as you go. Here's the same vacation-planning prompt built up iteratively:

IterationPrompt
1. TaskPlan a vacation.
2. + ContextPlan a vacation. I want to take a 5-day trip with two friends during the summer.
3. + Persona... Act like an experienced travel planner.
4. + Format... Organise the itinerary in a table with the day, activities, meals, and estimated costs.
5. + Tone... Use a fun and casual tone and prioritise affordable activities.
Don't front-load everything Adding all six elements to every prompt makes them unwieldy. Start with Task + one or two others. Only add more when the output isn't landing.

Prompt Engineering · 3 of 3

Chain of thought prompting

For complex, multi-step problems, asking the model to "think aloud" before answering produces more accurate results than asking it to jump straight to an answer.

What is chain of thought?

Chain of thought (CoT) prompting guides the model to break down a problem into intermediate steps — showing its reasoning before giving a final answer. This works because the model generates each token based on the previous ones: if it "thinks out loud," later tokens benefit from that reasoning.

Without CoT

Prompt: "A shop sells 3 apples for $2. How much for 12?"

Model: "$6"

No reasoning shown — more likely to be wrong on harder problems.

With CoT

Prompt: "...Let's think step by step."

Model: "3 apples = $2, so 1 apple = $0.67. 12 apples = 12 × $0.67 = $8"

Reasoning surfaced — errors caught earlier.

How to trigger chain of thought

You don't need a special framework. A few phrases reliably activate step-by-step reasoning:

Let's think step by step.
Before answering, reason through this carefully.
Walk me through your reasoning first.
Before stating your final answer, recount [X].
Why this matters for agent skills The self-check you'll write later — "before stating your final count, recount the bullets you just wrote" — is chain of thought applied inside a skill's instructions. You're using the same technique to make the agent verify its own work before committing to an answer.

When to use it

  • Multi-step reasoning — math, logic, decision trees
  • Classification with nuance — the model needs to weigh competing factors before deciding
  • Self-verification — asking the model to check its own output (as in agent skills)
  • Not needed for — simple factual lookups, short creative tasks, format transformations

What is an agent?

Before building agent skills, you need to understand what agents actually are — and when to use them.

An agent is a system that independently accomplishes tasks on your behalf. Unlike a simple chatbot that responds to one message at a time, an agent can interpret intent, make decisions, call tools, and loop through steps — all without you directing every move.

Key distinction Using a chatbot or LLM that doesn't control the workflow is not an agentic workflow. For it to be agentic, the LLM must control how the system moves, not just respond within it.

When should you build an agent?

Agents shine when you have these characteristics. Click each card to see why it matters.

Complex decision-making

Multiple possible paths based on context.

Click to learn more
Why it needs an agent

A fixed script can't handle "if X then Y else Z" reliably across varied inputs. The LLM decides the path based on the actual situation, not a hard-coded rule.

Difficult-to-maintain rules

Many edge cases or very specific conditions.

Click to learn more
Why it needs an agent

When rules have dozens of exceptions and keep changing, maintaining them in code becomes a nightmare. An LLM with clear instructions handles edge cases gracefully.

Unstructured data

Text, emails, reviews, documents.

Click to learn more
Why it needs an agent

Traditional code needs structured inputs. LLMs can read a messy customer review, extract the sentiment, categorize the feedback, and summarize it — no parsing logic required.

Agentic workflow steps

When an agent handles a request, it follows a full loop. Click each step to expand it.

1
Interprets the user's intent
▼
What is the user actually asking for? This is where natural language understanding matters — the same goal can be phrased a dozen different ways.
2
Decides whether it has enough information
▼
Can it complete the task with what it knows, or does it need to call a tool to get more data? This is an active decision the LLM makes, not a preset condition.
3
Chooses whether to call a tool
▼
Search the web, query a database, call an API — the agent picks the right tool for what it needs. You define which tools are available in the agent setup.
4
Runs the tool and uses the results
▼
The tool's output is fed back to the agent. Now it decides: is this enough to answer, or does it need another tool call? This loop can run multiple times.
5
Builds the final answer
▼
With all the information gathered, the agent assembles a final response in whatever format you specified in the instructions.

Writing effective descriptions

The description field is how your agent decides whether to use the skill at all. It's the most critical field for discovery.

Always write in third person The description is injected directly into the system prompt. "I can help with PDFs" breaks the system prompt's voice. Use "Processes PDF files and extracts text."

A good description includes:

  1. What the skill does — the action it performs
  2. When to use it — specific triggers and contexts
  3. Key terms — words a user might say that should activate it

Conciseness & degrees of freedom

The context window is shared. Every token in your skill competes with conversation history, other skills, and the user's request.

Why conciseness matters — mechanically

When Claude loads your skill, its contents go into the context window. That window is finite. The more tokens your skill uses, the less room there is for the actual conversation, other skills, and the user's request. This isn't just aesthetics — verbose skills can push out the context that Claude needs to do the task well.

The default assumption Claude already knows how PDFs work, what JSON is, and what "classify" means. Only add context Claude doesn't already have. For every sentence, ask: "Does Claude really need this?"

Best Practices · 2 of 3

Progressive disclosure

Claude doesn't load your entire skill upfront — just the metadata. SKILL.md is a table of contents, not the full encyclopedia.

The core idea

The context window is loaded in stages. Understanding what is loaded when explains every progressive disclosure decision.

Click through the stages to see what's in the context window at each point.
System prompt + conversation history
Skill names & descriptions (all skills)
SKILL.md body (matched skill only)
Reference file (e.g. FORMS.md — if needed)
Why this matters for how you write skills The description is the only thing Claude sees for most skills, most of the time. SKILL.md is only read when the skill is matched. Reference files are only read when explicitly needed. Design your skill with this loading order in mind.

The resources folder pattern

For larger skills, move detail into linked files. SKILL.md points to them; Claude only loads what's needed.

pdf-skill/
  SKILL.md          ← always loaded when skill matches
  FORMS.md          ← only loaded if user asks about forms
  REFERENCE.md      ← only loaded if user asks for API details
  scripts/
    analyze_form.py ← executed directly, never loaded into context

This structure means a skill can have comprehensive documentation without bloating the context window on every call. A form-filling question loads FORMS.md; a text extraction question doesn't. Scripts are executed, never read — so their size doesn't matter at all.

Keep references one level deep SKILL.md → FORMS.md ✓    SKILL.md → advanced.md → details.md ✗
Claude may not follow nested links fully. All reference files should link directly from SKILL.md.

Order the stages

Drag to arrange in the correct loading order.

  • ⠿Claude reads SKILL.md body and follows any linked files it needs
  • ⠿Agent starts up — name + description of all skills loaded into system prompt
  • ⠿Claude executes the instructions and produces output
  • ⠿User sends a request — Claude matches it to the right skill via description

Quick reference: anti-patterns to avoid

First-person descriptions

❌ "I can help you…"   ✓ "Extracts text from…"

Too many options, no default

❌ "You can use pypdf, pdfplumber, PyMuPDF…"   ✓ "Use pdfplumber. For scanned PDFs, use pdf2image."

Over-explaining what Claude knows

❌ Defining what a PDF is.   ✓ Just give the code.

Deeply nested references

❌ SKILL.md → advanced.md → details.md   ✓ SKILL.md → ref1.md, ref2.md (one level)
