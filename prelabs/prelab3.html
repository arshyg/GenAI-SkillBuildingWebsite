Foundations · 1 of 3

Why evaluate at all?

A skill is only as good as its ability to be checked. Before you can improve a skill, you need precise words for the pieces of a check — "test case" alone isn't enough.

You already know the basic building block: a test case is an input, an expected behavior, and a pass/fail condition. That's correct — but the field uses more specific words for what happens when you actually run one, and those words matter once you're running many test cases across many runs.

Why this matters "The skill failed" is vague. "Trial 3 of task 7 failed the budget grader because the transcript shows a stale currency-conversion tool call" is something you can actually act on.

Two jobs for an eval suite

The same skill needs two different kinds of eval, asking opposite questions — and expecting opposite pass rates.

Capability eval

Asks: "What can this skill do well?" Deliberately hard tasks. Should start low — that's the hill you're climbing, not a failure.

Regression eval

Asks: "Does it still do what it used to?" Tasks it already solves. Should sit near 100% — a drop means something broke.

A common mix-up A low score on a capability eval is expected progress. A low score on a regression eval is a bug. Mixing the two into one number hides which one you're looking at.

pass@k vs. pass^k

Outputs vary run to run, so "did it pass?" is really a question about probability across trials — and there are two very different ways to report it.

pass@k

At least one success in k tries. Rises toward 100% as k grows. Use when one success is enough.

pass^k

Every one of k tries succeeds. Falls toward 0% as k grows. Use when the skill must be reliable every single time.

Grading methods — code, model, or human

"Manual vs. automated" is the beginner version. Real eval suites mix three kinds of graders, each with a different failure mode.

Click each card to flip it.

Code-based

Click for pros/cons

Regex, unit tests, static analysis. Fast, cheap, objective. Brittle to valid variation it wasn't written for.

Model-based

Click for pros/cons

Rubric scoring, pairwise comparison. Flexible, scales to open-ended output. Needs calibration against humans.

Human

Click for pros/cons

SME review, crowdsourced judgment. The gold standard. Doesn't scale, expensive, slow.

Grade the outcome, not the exact steps Agents often find valid paths you didn't anticipate. Checking whether the right thing happened is usually more robust than checking whether it happened in the exact sequence you expected.

Deep Dive · 1 of 3

Deterministic checks

When a check has a concrete, computable answer, use it — it removes an entire category of grading mistake.

Deterministic evals are for exactly the things that don't need judgment: is a turn cap being upheld, does a required field exist, does a number fall in range. Reach for these whenever you can — LLMs can make mistakes, and it's more reliable to compute an answer than to ask a model to judge one.

def check_turn_cap(transcript, max_turns=5):
    return len(transcript) <= max_turns

No ambiguity, no judgment call — just count and compare. Click each transcript below to run the check.

4-turn transcript
check_turn_cap(t, max_turns=5)

✓ True — 4 ≤ 5, within cap

5-turn transcript
check_turn_cap(t, max_turns=5)

✓ True — 5 ≤ 5. Boundary case: <= includes the cap itself.

7-turn transcript
check_turn_cap(t, max_turns=5)

✗ False — 7 > 5, exceeded the cap by 2 turns

Rule of thumb If you can write the check as code without a model in the loop, do that first. Save LLM-as-a-judge for the things that genuinely need judgment.

Deep Dive · 2 of 3

LLM-as-a-judge

Using a model to score outputs against a rubric instead of a human grading every run. Powerful — and easy to trust more than it deserves.

Why it's worth using

It scales to many test cases and iterations, and can be more consistent than ad hoc human grading. It's the same "evaluation dimensions" thinking from prompt rubrics, now automated.

Two ways to run it

On a transcript

Grade a recorded run after the fact — cheaper, repeatable, good for regression checks.

In a live simulation

Grade the skill as it runs, sometimes interacting with it — closer to production, more expensive.

Failure modes to watch for Judge bias (favors verbose, confident-sounding answers over correct ones) · vague rubrics that produce inconsistent scores · the judge model itself needing validation against human judgment.

Mitigations that actually help

  • Give the judge an explicit "Unknown" option — reduces pressure to invent a confident-sounding verdict
  • Grade one dimension per call rather than asking one judge prompt to score everything at once
  • Recalibrate against your own human read on a cadence — not just once, since judges drift

Spot the difference — which rubric would you trust more?

Click each card to see how it actually performs as a judge prompt.

Verbose rubric

"Please carefully read the response and think about whether it seems like a good, helpful, high-quality answer that a knowledgeable person would be satisfied with, considering the overall tone and thoroughness."

❌ No concrete criteria, no scale, no definition of "good." Two runs of this judge on the same output can land on different scores — and it's exactly the kind of prompt that lets verbosity pass for quality.

Concise rubric

"Score groundedness 1–5: does every number in the response trace to a value in the transcript? 5 = all do. 1 = none do. If you can't tell, answer Unknown."

✓ One dimension, a concrete check ("traces to a value"), defined endpoints, and an escape hatch. Two runs are far more likely to agree.

The pattern to notice This is the same lesson as concise prompting generally: specificity beats volume. A longer rubric isn't a more careful one — it's usually a vaguer one wearing more words.

Deep Dive · 3 of 3

GEPA — automating the rewrite loop

Evaluations and judge scores aren't the end goal — they're the signal an optimizer improves against.

GEPA (reflective prompt evolution) improves a skill's instructions automatically: it reads a failed trial's transcript, reflects on why it failed in plain language, and rewrites the instructions — instead of a human manually tuning the prompt by hand each time.

⚡

vs. reinforcement learning (GRPO)

Up to 35× fewer rollouts for a comparable or better result.

📈

vs. the prior best optimizer (MIPROv2)

10–14% higher scores in the paper's own benchmarks.

Model quality matters unevenly The reflection model should be strong — it's doing the real diagnostic reasoning. The optimizer loop and the judge scoring failed attempts can run on cheaper models.

Why GEPA keeps more than one "best" prompt

Different instruction variants are often strong on different subsets of cases. Picking one "best average" quietly gives up whatever that variant is weak on.

case 1case 2case 3case 4
Variant A✓✓✗✗
Variant B✗✗✓✓

GEPA keeps both — this is the Pareto frontier — and can graft B's strength onto A rather than throwing either away.

Spot the difference — which instruction actually gets followed?

Original (failing)

"Please be sure to take into account all of the various dietary needs and preferences that a traveler might have when constructing their itinerary."

❌ "Various dietary needs" never names anything. The skill handled vegetarian requests and silently dropped gluten-free — nothing here told it gluten-free was a thing to check.

GEPA's rewrite

"Flag vegetarian and gluten-free options for every day of the itinerary."

✓ Shorter, and it actually names the constraint that was silently failing. Score on the failing case: 2/4 → 4/4.

Best Practices · 1 of 2

Observability, tracing & open-source tooling

When an eval fails, tracing is how you find out where — instead of guessing. You also don't have to build any of this from scratch.

Observability means seeing inside a skill run: which subagent was called, what tool calls happened, latency, token counts — not just the final output. This ties directly to last week's subagents and loops: a loop that never converges, or a subagent that returns bad output, both look identical from the outside unless you can see the steps.

Same failed run, two ways of looking at it

Basic print logging
[log] subagent: itinerary_builder started
[log] tool_call: search_flights → ok
[log] tool_call: convert_currency → ok
[log] subagent: itinerary_builder finished
Structured trace
subagent: itinerary_builder · 2.4s total
tool_call: search_flights · 240ms
⚠ convert_currency · JPY→USD rate from a 14-day-old cache
subagent finished, returned itinerary

Every step "succeeded" in the print log. Only the trace shows which step actually caused the failed budget check downstream — not more data, attributable data.

Tracing & observability tools

OpenTelemetry

Open standard for traces and spans. Vendor-neutral.

Langfuse

Open-source (MIT), self-hostable tracing built for LLM apps.

Arize Phoenix

Source-available observability for LLM apps. Note: Elastic License 2.0, not OSI-approved open source — check this matters for your use case.

Braintrust

Combines offline eval with production monitoring in one platform.

Open-source evaluation frameworks

You don't have to hand-roll a harness. These are the ones worth knowing about, each suited to a different shape of eval:

DeepEval

Apache-2.0. Pytest-style assertions — write evals as ordinary test functions. Broad metric coverage (G-Eval, agent, multi-turn).

Promptfoo

MIT. YAML config + CLI — good for prompt regression testing in CI, one file per test suite, includes red-team plugins.

Inspect AI

MIT, from the UK AI Safety Institute. Python task files — the closest thing to a standard for rigorous model/agent benchmarking.

Ragas

Apache-2.0. Purpose-built for RAG pipelines — faithfulness, context recall/precision. Worth it if your skill retrieves before it answers.

Which one for the Week 3 lab For a first real harness around the trip-planning skill, DeepEval's pytest style maps most directly onto "test case = input + expected behavior + pass/fail condition" — you'll recognize the shape immediately.

Best Practices · 2 of 2

Things to watch out for

Three habits that quietly undermine everything above, even when each individual step looks correct.

Overfitting to your test cases

Tuning a skill until it passes your specific test cases without actually generalizing. Write test cases from real observed failures, not to make a number go up — and keep a held-out set the optimizer never sees.

Trusting the judge blindly

Judges drift and can favor confident, verbose answers over correct ones (§4). Spot-check judge scores against your own read on a regular cadence — not just the first time you write the rubric.

Ignoring which model you're optimizing for

Models vary in how well they follow negative framing ("DO NOT…") versus affirmative framing ("Only include…"). The same instruction can score differently depending on the model — test any rewrite across every model you plan to deploy with, not just the one you drafted against.
