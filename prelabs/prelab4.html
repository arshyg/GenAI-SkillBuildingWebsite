Overview

MCP, RAG & Memory

Three techniques that extend what an agent knows and what it can reach — without changing the model itself.

By now you can build agents, delegate to subagents, loop for quality, and chain skills. But agents are still limited to what's in their context window and what tools you've hand-coded. These three techniques break those limits.

MCP

Extends reach

A standard protocol for connecting agents to any external tool, data source, or service — without custom integration code for each one.

RAG

Grounds knowledge

Retrieves relevant chunks from a document store at inference time and injects them into the prompt — so the model answers from evidence, not memory.

Memory

Personalizes over time

Stores and retrieves what the agent knows about the user — within a session (short-term) or across many sessions (long-term).

How they relate

TechniqueProblem it solvesWhere it lives
MCP"My agent can't access external systems"Between agent and external services
RAG"My agent doesn't know the right facts"Inside the prompt, at inference time
Memory"My agent forgets who the user is"Across turns and across sessions

MCP · 1 of 3

MCP concepts

Model Context Protocol is a standardized way for LLM-based agents to connect to external tools, data sources, and services — without writing custom integration code for each one.

Why standardization matters

Before MCP, connecting an agent to a new tool (a database, a calendar, a code executor) meant writing a one-off integration — custom auth, custom API calls, custom error handling — for every tool. MCP defines a single protocol that any tool can implement once, and any agent can use.

The USB analogy Before USB, every peripheral needed its own port. USB standardized the interface — any device, any computer, one plug. MCP does the same for agents and tools.

MCP in skills

How to reference an MCP tool inside a skill's instructions — and the key rules for doing it right.

Referencing an MCP tool in a skill

When a skill needs to call an MCP tool, the instructions should specify the full tool name (server:tool), what to pass it, and what it returns. Don't leave any of this to inference.

---
name: checking-weather
description: >
  Retrieves current weather for a given city. Use when the user asks
  about weather, temperature, or conditions in any location.
---

## Instructions

You are a weather assistant. When given a city name:

1. Call the WeatherServer:get_forecast tool with:
   - city: the city name from the user's request
   - units: "metric"

2. The tool returns: temperature (°C), conditions, humidity, wind speed.

3. Summarise the weather in one friendly sentence.
   Format: "[City] is currently [conditions] at [temp]°C."
Always use fully qualified tool names WeatherServer:get_forecast, not just get_forecast. Without the server prefix, the agent may fail to locate the tool when multiple MCP servers are connected.

What makes a good MCP tool call in a skill

Name the server explicitly

Server:tool format every time.

Click — why?
Why it matters

Multiple servers can have tools with the same name. The prefix tells the MCP client exactly which server to route to — no ambiguity.

Specify every parameter

List what to pass and where it comes from.

Click — why?
Why it matters

The agent won't guess well. If the skill says "call get_forecast with the city", the model doesn't know the parameter name, type, or format expected by the server.

Describe what it returns

Tell the agent what the output looks like.

Click — why?
Why it matters

The agent needs to parse and use the tool's output. If it doesn't know the structure, it may miss fields or misformat the response.

Handle tool failure

Specify what to do if the tool errors.

Click — why?
Why it matters

External tools fail. If the skill says nothing, the agent either halts or makes something up. Tell it: "If the tool returns an error, tell the user the data is unavailable and ask them to try again."

RAG · 1 of 3

RAG concepts

Retrieval-Augmented Generation grounds a model's output in external documents at inference time — so it answers from evidence, not just training.

Why RAG instead of just putting docs in the prompt?

You can't fit a 10,000-page knowledge base into a context window. Even if you could, most of it is irrelevant to any given question — and irrelevant context degrades output quality.

Without RAG

Model answers from training data. Fine for general knowledge, breaks for proprietary or recent information.

With RAG

Model retrieves the relevant chunks first, then answers using them as evidence. Works for any document store, any domain.

The key insight: retrieval as a skill

RAG isn't a model technique — it's a pipeline you build. The model's job is still generation. The retrieval step is a separate system (often a vector database) that finds the right evidence before the model even sees the question.

Where RAG fits in your agent system RAG is typically implemented as a tool or subagent. Your skill calls retrieve_docs(query), gets back relevant chunks, injects them into the prompt, and then generates the answer. The model never "knows" the documents — it only sees what retrieval surfaces.

RAG · 2 of 3

The RAG pipeline

Six steps from raw documents to a grounded answer. Each step has a clear job — and a clear failure mode.

1

Chunking

Split source documents into small, overlapping pieces. Too large: retrieval is imprecise. Too small: chunks lose context. Typical: 256–512 tokens with 10–20% overlap.

2

Embedding

Convert each chunk into a vector (a list of numbers) using an embedding model. Semantically similar chunks get vectors that are close together in vector space.

3

Indexing

Store the vectors in a vector database (e.g. Pinecone). The database is optimised for fast nearest-neighbour search — finding which vectors are closest to a query vector.

4

Retrieval

At inference time, embed the user's query using the same embedding model. Fetch the top-k chunks whose vectors are closest to the query vector. Typically k = 3–10.

5

Augmentation

Insert the retrieved chunks into the prompt as context, before the user's question. The model now has evidence to reason from.

6

Generation

The model reads the retrieved context and the question, then generates an answer grounded in the evidence. It can cite specific chunks if instructed to.

Order the pipeline

Drag the steps into the correct order.

  • ⠿Augmentation — insert chunks into the prompt
  • ⠿Embedding — convert chunks to vectors
  • ⠿Generation — model answers using retrieved context
  • ⠿Chunking — split documents into small pieces
  • ⠿Retrieval — embed query and fetch top-k similar chunks

RAG · 3 of 3

RAG evaluations

Building a RAG pipeline is the easy part. Knowing whether it's working is harder. Two metrics tell you most of what you need to know.

The two core metrics

Context recall

Did retrieval find what was needed?

What fraction of the relevant information that exists in your document store actually got retrieved? Low recall = the right chunks weren't found.

Low recall → fix chunking or increase k
Context precision

Was what was retrieved actually useful?

What fraction of the retrieved chunks were actually relevant to the query? Low precision = lots of noise flooding the context.

Low precision → refine chunking or decrease k

Interpreting the scores

RecallPrecisionWhat it meansFix
HighHighIdeal — found the right chunks, nothing else—
LowHighPrecise but incomplete — missing relevant chunksIncrease k, re-chunk
HighLowComplete but noisy — too much irrelevant contextDecrease k, smaller chunks
LowLowWrong chunks entirely — embedding or indexing problemCheck embedding model

Memory · 1 of 3

Memory concepts

Memory is what the agent knows about the user — within a conversation (short-term) or across many sessions over time (long-term).

Short-term vs long-term memory

Short-term

Within a session

What the agent learned during this conversation. It's in the context window. When the session ends, it's gone unless explicitly saved.

Example: "The student mentioned they have an exam on Thursday three messages ago — keep answers concise."
Long-term

Across sessions

Persisted facts about the user, written to a store after each session and retrieved at the start of the next one.

Example: "This student prefers visual explanations with worked examples and studies best in 45-minute blocks."

Why memory matters

Without memory, every session starts from scratch. The user has to re-explain their preferences, context, and constraints every time. With long-term memory, the agent already knows who it's talking to — and the experience feels personal rather than generic.

Memory as a form of personalization at scale A skilled human assistant remembers your preferences without being asked. Memory gives your agent the same capability — not by making the model smarter, but by giving it the right context at the right time.

Memory · 2 of 3

Memory patterns in skills

Three ways memory integrates with agent skills — each with a different role and a different place in the workflow.

🎯

Memory as a trigger for skill selection

Helps the orchestrator decide which skill to invoke

▼

The orchestrator reads memory before deciding what to do. Stored preferences change which skill gets called.

Example

Memory says: "user_prefers_concise: true"
Orchestrator reads this → calls summarizing-response skill at the end of every reply instead of returning the full answer directly.

When to use it When a preference should change the flow of the whole interaction — not just one response.
⚙️

Memory as a parameter for skills

Skill uses memory as input to personalise the response

▼

Memory is passed into the skill as part of the input. The skill is the same for every user — the memory is what makes the output personal.

Example

Memory says: "email_signoff: 'Sincerely, Alex'"
The drafting-email skill receives this as a parameter → appends "Sincerely, Alex" to every email without being asked.

## Instructions
Draft a professional email for the user.

User memory:
- Preferred sign-off: {memory.email_signoff}
- Preferred tone: {memory.email_tone}

Always use the sign-off and tone from memory.
✍️

Skills that write to memory

Focused on updating memory based on the conversation

▼

Some skills exist specifically to extract and store facts about the user. They run in the background after interactions and update the memory store.

Example

After a study session, the updating-student-profile skill runs and writes:
{"learning_style": "visual", "preferred_session_length": "45min", "weak_subjects": ["calculus"]} to the memory store.

Be explicit about what gets written Don't let the agent write whatever it infers. Define exactly which fields the memory-writing skill updates, and what evidence it needs before writing. Vague writes create noisy, unreliable memory.

Watch out for

Things to watch out for

MCP, RAG, and memory each introduce failure modes that don't exist in simpler agent systems. Know them before you build.

Memory bloat

Just like context bloat from Week 2, memory stores can grow unbounded — accumulating redundant, contradictory, or stale facts over time. A memory store that keeps everything eventually becomes too noisy to be useful.

Symptoms
  • Agent pulls old, outdated preferences that contradict what the user just said
  • Memory retrieval returns too many results and floods the context
  • Conflicting facts in memory cause inconsistent agent behavior
Mitigations
  • Write memory with timestamps — prefer recent over old
  • Limit the number of active memory entries per category
  • Run a periodic "memory consolidation" skill that merges and de-duplicates

Skill drift

As the agent learns more about the user, its behavior can drift further and further from the original skill design. A skill built for a general audience starts behaving very differently for a heavily-profiled user — sometimes in ways you didn't intend.

Example

Memory says the student prefers concise answers. Over time, the explanation skill starts giving one-line answers — technically following the preference, but now too brief to actually teach anything. The skill has drifted.

Mitigation

Set hard constraints in the skill instructions that memory parameters cannot override: "Regardless of length preferences, explanations must include a definition, an example, and a summary."

MCP tool trust

Not all MCP servers are trustworthy. A compromised or malicious server could return crafted responses that prompt-inject the agent. Always validate MCP tool outputs before passing them into further reasoning — especially if the server is external or community-provided.

RAG retrieval without grounding instructions

Retrieving relevant chunks is only half the job. If the prompt doesn't explicitly tell the model to use the retrieved context — or to say "I don't know" when context is insufficient — the model will default to training memory and hallucinate. Always include: "Answer only using the context below. If the context doesn't contain the answer, say so."
